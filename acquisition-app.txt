# ✅ 1) Big Picture Architecture (How the project is organized)

Your project is a **Spring Boot monolith**, but internally it is designed like a clean enterprise system:

### **API Layer**

➡️ Controllers + DTOs
**Only responsible for HTTP request/response**

### **Application Layer**

➡️ Services + Facade
**Responsible for orchestration + use-cases**

### **Workflow Layer**

➡️ Engine + transition + validation + resolvers

-- Optional (recommended) for UUID generation:
-- CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
-- Or use pgcrypto:

-- ==============================
-- 1) REQUEST
-- ==============================
CREATE TABLE da_request (
    request_id              uuid PRIMARY KEY,
    request_number          varchar(50) UNIQUE NOT NULL,
    title                   text,
    description             text,

    requester_user_id       varchar(200) NOT NULL,
    requester_name          varchar(200),

    status                  varchar(50) NOT NULL,
    current_stage_code      varchar(100) NOT NULL,

    is_completed            boolean NOT NULL DEFAULT false,

    created_at              timestamptz NOT NULL DEFAULT now(),
    created_by              varchar(200) NOT NULL,
    updated_at              timestamptz NOT NULL DEFAULT now(),
    updated_by              varchar(200) NOT NULL,

    row_version             int NOT NULL DEFAULT 0
);

CREATE INDEX idx_da_request_status ON da_request(status);
CREATE INDEX idx_da_request_requester ON da_request(requester_user_id);
CREATE INDEX idx_da_request_current_stage ON da_request(current_stage_code);


-- ==============================
-- 2) STAGE DEFINITIONS
-- ==============================
CREATE TABLE da_stage_definition (
    stage_code              varchar(100) PRIMARY KEY,
    stage_name              varchar(200) NOT NULL,
    stage_order             int NOT NULL,

    requires_excel_upload   boolean NOT NULL DEFAULT false,
    excel_template_name     varchar(200),

    is_active               boolean NOT NULL DEFAULT true,

    created_at              timestamptz NOT NULL DEFAULT now(),
    created_by              varchar(200) NOT NULL
);

CREATE UNIQUE INDEX uq_da_stage_definition_order ON da_stage_definition(stage_order);


-- ==============================
-- 3) REQUEST STAGE INSTANCE
-- ==============================
CREATE TABLE da_request_stage (
    request_stage_id        uuid PRIMARY KEY,
    request_id              uuid NOT NULL REFERENCES da_request(request_id),
    stage_code              varchar(100) NOT NULL REFERENCES da_stage_definition(stage_code),

    stage_status            varchar(50) NOT NULL,
    stage_version           int NOT NULL DEFAULT 1,
    is_current              boolean NOT NULL DEFAULT true,

    submitted_at            timestamptz,
    submitted_by            varchar(200),

    approved_at             timestamptz,
    approved_by             varchar(200),

    rejected_at             timestamptz,
    rejected_by             varchar(200),
    rejection_reason        text,

    created_at              timestamptz NOT NULL DEFAULT now(),
    created_by              varchar(200) NOT NULL,
    updated_at              timestamptz NOT NULL DEFAULT now(),
    updated_by              varchar(200) NOT NULL,

    row_version             int NOT NULL DEFAULT 0
);

CREATE INDEX idx_da_request_stage_request ON da_request_stage(request_id);
CREATE INDEX idx_da_request_stage_stage ON da_request_stage(stage_code);
CREATE INDEX idx_da_request_stage_status ON da_request_stage(stage_status);

CREATE UNIQUE INDEX uq_da_request_stage_unique
ON da_request_stage(request_id, stage_code, stage_version);

CREATE UNIQUE INDEX uq_da_request_stage_current
ON da_request_stage(request_id, stage_code)
WHERE is_current = true;


-- ==============================
-- 4) STAGE DATA (persist only on SUBMIT)
-- ==============================
CREATE TABLE da_request_stage_data (
    stage_data_id           uuid PRIMARY KEY,
    request_stage_id        uuid NOT NULL REFERENCES da_request_stage(request_stage_id),

    payload_json            jsonb NOT NULL,
    payload_schema_version  int NOT NULL DEFAULT 1,

    created_at              timestamptz NOT NULL DEFAULT now(),
    created_by              varchar(200) NOT NULL
);

CREATE UNIQUE INDEX uq_da_stage_data_request_stage
ON da_request_stage_data(request_stage_id);


-- ==============================
-- 5) PREVIEW CACHE (optional)
-- ==============================
CREATE TABLE da_request_stage_preview_cache (
    preview_id              uuid PRIMARY KEY,
    request_id              uuid NOT NULL REFERENCES da_request(request_id),
    stage_code              varchar(100) NOT NULL REFERENCES da_stage_definition(stage_code),

    preview_type            varchar(50) NOT NULL,
    preview_key             varchar(200) NOT NULL,

    created_by              varchar(200) NOT NULL

CREATE INDEX idx_da_preview_request_stage ON da_request_stage_preview_cache(request_id, stage_code);
CREATE INDEX idx_da_preview_expiry ON da_request_stage_preview_cache(expires_at);

-- 6) UPLOADED FILES (Excel + attachments)
-- ==============================

Great question ✅ Rishikesh.
Your app can easily become slow because it has **workflow + approvals + large business data + excel uploads + external API calls**.

Below are the **best practical ways** to keep it fast (without over-engineering).

---

# ✅ 1) Keep UI “load request” APIs lightweight

### Problem

If UI opens an existing request and backend loads **all business tables + approvals + timeline + stage data** in one API → slow.

### Recommendation

Split into small APIs:

* **Request Header API** (fastest)
* **Current Stage Status API**
* **Stage Data API (only that stage)**
* **Approvals API**
* **Timeline API (lazy load / pagination)**

✅ UI loads fast and fetches details on demand.

---

# ✅ 2) Avoid N+1 queries in JPA

### Common issue

Business model has many relationships (feed_group → datasets → attributes etc.)

### Fix

Use:

* `@EntityGraph` for controlled eager fetch
* custom JPQL/SQL queries for heavy screens
* avoid `FetchType.EAGER` globally

✅ Big improvement.

---

# ✅ 3) Use pagination everywhere

Mandatory for:

* Existing request list
* Approve pending list
* Audit timeline
* Dataset lists under a feed group

Use:

* `Pageable`
* `LIMIT/OFFSET`

✅ prevents full table scans.

---

# ✅ 4) Indexing (most important DB speed lever)

You already have some indexes in technical model.

Add indexes on frequently queried fields like:

* `da_request(status)`
* `da_request(requester_user_id)`
* `da_request(current_stage_code)`
* `da_approval_task(approver_user_id, status)`
* `da_request_stage_assignee(assignee_user_id)`

For business model:

* always index `request_id` bridge columns

✅ This alone keeps app fast under load.

---

# ✅ 5) Don’t store huge stage JSON unnecessarily

Your `da_request_stage_data.payload_json` can become large.

Suggestions:

* store only **required fields**
* avoid storing duplicate reference data inside payload
* keep schema versioning to evolve

✅ less DB size + faster reads.

---

# ✅ 6) External API calls must be fast and protected

Your preview APIs call:

* HRI
* AppDir
* DGP

### Best practices:

* timeouts (connect + read)
* retries only for safe errors (like timeouts)
* circuit breaker (optional)
* caching for repeated lookups (short TTL)

Example:

* cache tenant details for 10 minutes
* cache dataset info for 10 minutes

✅ prevents slow UI experience.

---

# ✅ 7) Use async processing for heavy tasks

Things that can be async:

* email notifications
* webhook/Teams notifications
* audit enrichment
* large excel validation report generation

Keep core submit synchronous, but move extras async using:

* `da_outbox_event` table (best)
* background scheduler/worker

✅ submit stays fast.

---

# ✅ 8) Excel upload performance tips

Excel parsing can become heavy.

Do:

* validate file size limit
* stream parsing if possible
* validate row count limit (ex: max 5k rows)
* parse + persist in batch inserts

✅ avoids JVM memory spike.

---

# ✅ 9) Use proper transaction boundaries

Don’t wrap everything in one huge transaction.

Example:

* Stage submit transaction should include only DB writes required
* Notification/outbox can be separate

✅ reduces lock time and contention.

---

# ✅ 10) Observability from start (so you can detect slowness)

Add:

* request correlation id
* API response time logs
* slow query logs (hibernate)
* metrics (Micrometer + Prometheus later)

This helps you identify:

* which API is slow
* which query is slow
* which external API is slow

✅ keeps performance under control.

---

If you implement only these, your app will be fast:

1. Pagination on lists
2. Indexing on technical + bridge `request_id`
